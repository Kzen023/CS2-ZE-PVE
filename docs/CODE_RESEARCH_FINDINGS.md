# Code Research Findings for ZEPVE

This document records architecture and engineering conclusions from reading mature CS2 / Source 2 projects relevant to ZEPVE.

The goal is not to copy implementations. The goal is to preserve proven engineering patterns while keeping ZEPVE ZE-first, small, observable and easy to roll back.

## 1. Executive conclusions

The current ZEPVE direction remains valid:

```text
Core owns lifecycle
BotAI owns who to pursue and awareness assistance
Navigation owns how to reach the assigned target
Map owns ZE map semantics and runtime map state
HUD consumes state; it does not discover map entities itself
```

The main gaps identified by this research are:

1. a unified runtime player/zombie identity and lifecycle boundary;
2. explicit migration-time writer handoff so legacy and replacement systems never execute the same responsibility concurrently;
3. bounded diagnostic history so Bot failures can be explained after they happen;
4. a narrow Valve Bot profile adapter behind BotAI;
5. a compiled map runtime model instead of ad-hoc entity lookup from multiple modules;
6. real-world ZE configuration corpora for compatibility testing.

These should be added without creating unnecessary new repositories or DLLs.

Migration-time execution ownership is documented separately in `MIGRATION_AUTHORITY.md` and takes priority whenever a responsibility is being transferred from legacy code.

## 2. CS2KZ — lifecycle dispatch and recording discipline

The strongest lesson from CS2KZ is its ownership and lifecycle model.

A player object receives engine movement/user-command lifecycle callbacks and dispatches them to player-owned services in an explicit order. Initialization, reset and destruction are also explicit rather than being discovered lazily from unrelated per-tick code.

### Apply to ZEPVE

Core should introduce lightweight runtime identity/context state:

```text
ZepvePlayerContext
├─ stable player identity
├─ connection generation
├─ current controller/pawn generation
├─ role: Human / ZombieBot
├─ lifecycle state
└─ module-owned handles

ZombieContext
├─ Bot identity
├─ BotAI state handle
├─ Navigation state handle
└─ diagnostics identity
```

The context is not a shared bag of writable module state. Core owns identity and lifecycle; BotAI and Navigation still own their own data.

Delayed actions need more than one spawn counter. The relevant validity scope may include:

```text
plugin lifetime
map epoch
round epoch
connection identity/generation
pawn/spawn generation
optional target/binding version
```

Expected lifecycle flow:

```text
player disconnect / pawn replacement / round or map change
→ Core invalidates the relevant lifetime
→ BotAI releases target/awareness state
→ Navigation releases route/movement state
→ stale timers and delayed callbacks are rejected
```

This is preferable to every module repeatedly rediscovering whether a controller, pawn or entity reference is still valid.

Core should first prove this identity/invalidity model while legacy remains the gameplay writer. Gameplay authority is transferred later, one responsibility at a time.

### Bounded recording

CS2KZ also demonstrates a useful separation between:

- continuously retained circular history;
- event records;
- high-frequency movement data;
- longer persistent recordings;
- background serialization/file I/O.

ZEPVE should use the same idea for diagnostics before attempting sophisticated replay systems.

## 3. Add a Bot Flight Recorder early

ZEPVE needs a bounded diagnostic recorder that is separate from normal logging, Runtime Trails and Recorded Routes.

```text
RuntimeTrail
= navigation input generated by humans

RecordedRoute
= reviewed persistent route data

MotionClip
= optional future high-detail movement data for difficult sections

FlightRecorder
= recent evidence explaining why a Bot failed
```

Suggested per-zombie rolling samples:

```text
Time
Position
Velocity
AssignedTarget
ValveEnemy
EnemyVisible
NavigationDriver
RouteSource
RouteSegment
RouteNode
TargetDistance
ProgressDelta
RecoveryLevel
AwarenessState
```

Suggested transition events:

```text
TargetChanged
NativeNavUnavailable
NativeNavNoProgress
TrailFallback
TrailSegmentChanged
RecoveryEscalated
RecoveryTeleport
ReacquireStarted
ReacquireSucceeded
ReacquireFailed
```

Keep history bounded, for example by time or fixed capacity. Do not write it to disk continuously.

Useful commands:

```text
css_zepve_status
css_zepve_bot <slot>
css_zepve_ai <slot>
css_zepve_nav <slot>
css_zepve_events [filter]
css_zepve_dumpbot <slot> [seconds]
```

The normal logger remains responsible for durable operational logs. The Flight Recorder is responsible for short-term diagnosis.

Do not create a separate `ZEPVE.Diagnostics.dll` for this baseline. Keep shared diagnostic contracts/data small and colocated until independent ownership is justified.

## 4. vsBots — use Valve Bot profiles through a narrow adapter

vsBots shows that useful behavior can be controlled through Valve Bot profile state rather than replacing all Bot behavior.

Relevant concepts include aggression, skill/teamwork, reaction time, attack delay and look/aim behavior. It also demonstrates dynamic Bot profile creation instead of requiring manual edits to Valve profile files.

### Apply to ZEPVE

Add a small BotAI profile layer:

```text
ZEPVE.BotAI
└─ Profiles/
   ├─ ZombieBotProfile
   ├─ BotProfilePolicy
   └─ IValveBotProfileAdapter
```

V1 should have one production profile concept, not a class hierarchy of zombie types.

```text
ZEZombie
```

Only parameters proven useful in runtime testing should be changed. Keep Valve defaults for everything else.

The intended future difficulty path is:

```text
Director chooses difficulty/pressure
→ BotAI BotProfilePolicy translates AI difficulty
→ IValveBotProfileAdapter applies supported Valve fields
```

Director should not directly write arbitrary Valve Bot memory.

Offsets/signatures/profile internals are unstable engine dependencies. Validate them in ZEPVE-Lab first and make production use optional/fail-soft.

## 5. StripperCS2 — compile configuration into a runtime map plan

StripperCS2 demonstrates an important map architecture pattern:

```text
configuration
→ parse/validate at level initialization
→ domain actions
→ runtime application
```

It treats entity keyvalues and Entity I/O as structured data rather than scattering targetname searches throughout unrelated systems.

### Apply to ZEPVE.Map

Use this flow when Map complexity actually requires it:

```text
MapConfig
→ MapDefinition
→ MapPlanCompiler
→ MapPlan
→ MapRuntime
```

`MapPlan` should contain already parsed and validated data needed by the current map, for example:

```text
MapPlan
├─ StageSignals
├─ RespawnSignals
├─ NukeSignals
├─ BossDefinitions
├─ TeleportTransitions
├─ UnsafeRecoveryZones
└─ NavigationOverrides
```

Introduce one reusable entity selector model:

```text
MapEntitySelector
├─ ClassName?
├─ TargetName?
├─ HammerId?
└─ OutputSignature?
```

Selector semantics still need to define multi-field AND/OR behavior, zero/multiple matches and rebind behavior after templated entity creation/replacement.

Avoid separate implementations of `FindByTargetName`, HammerID matching and counter discovery in HUD, Map, Navigation and other modules.

Map configuration must be loaded/validated outside hot paths. One malformed map override should produce a clear error and a controlled fallback rather than breaking unrelated runtime systems.

Do not block early Core migration on a complete MapPlan compiler. Implement the minimum trustworthy map/round signals first when Core authority actually needs them.

## 6. GFL ZE configuration corpus — test against real maps

Real ZE configuration repositories contain established conventions around:

- targetnames;
- Hammer IDs;
- templated entities;
- counters;
- breakables;
- Entity I/O;
- Stripper modifications;
- Boss HUD metadata;
- per-map server configuration.

ZEPVE should not invent custom authoring requirements when an established ZE convention can be imported or adapted safely.

Preferred policy:

```text
auto-detect when reliable
→ reuse established ZE conventions where practical
→ require ZEPVE-specific overrides only for missing/ambiguous information
```

Add a compatibility corpus under tests when Map work begins. It should validate real-world map/config data, not only synthetic examples.

## 7. BossHud — separate config, runtime state and rendering

BossHud reinforces a clean three-stage design:

```text
Boss configuration
→ runtime Boss object/state
→ HUD rendering data
```

Entity discovery belongs to the map/runtime side. Rendering should consume stable domain state.

### Apply to ZEPVE

HUD should consume contracts such as:

```text
IMapStateApi
IBossStateApi
```

HUD should not search for `math_counter`, Hammer IDs, targetnames or map outputs.

Similarly, Map should publish stage/Boss state without depending on one HUD implementation.

A useful Boss-state payload can remain small:

```text
Name
CurrentHealth
MaxHealth
Phase/Segment if required
Display flags
```

Keep map entity references internal to Map runtime.

## 8. SharpTimer Trails — borrow discontinuity detection, avoid hot-path allocation

SharpTimer Trails demonstrates a useful simple rule: large position discontinuities should not be represented as continuous trail edges.

ZEPVE should improve Trail segment detection using multiple sources:

```text
explicit teleport/map transition signal
→ strongest evidence

otherwise
large displacement
+ elapsed time
+ velocity/movement context
→ possible segment break
```

Do not use one fixed distance threshold as the entire rule because `trigger_push`, fast movement and unusual map mechanics can cause false positives.

Runtime Trail data must belong to one human identity/generation. The legacy shared/global point pool is useful as behavioral history but must not be copied as the final Navigation model.

Consumer cursors should use monotonic node sequence semantics rather than ring-buffer storage indexes that can later be reused.

### Do not copy the hot-path pattern

Avoid per-tick patterns such as:

```text
Get all players
→ LINQ Where/ToList
→ copy collections
→ repeated searches
```

Core should maintain stable human/Bot registry views. Navigation should iterate those views using allocation-light loops and bounded buffers.

## 9. CS2ServerGUI — bounded queryable debug state

A bounded event buffer with pause/clear/filter/detail inspection is more useful than unlimited debug log spam.

ZEPVE should implement a small in-memory event buffer and structured snapshots before considering any GUI.

Example Bot snapshot:

```text
Zombie #8
AssignedTarget : player
ValveEnemy     : null
EnemyVisible   : false

Awareness
  State        : Reacquiring
  Elapsed      : 0.47s

Navigation
  Driver       : Trail
  Source       : RuntimeTrail
  Segment      : 3
  Node         : 142
  Progress     : +81u / 1s
  Recovery     : PostTeleport

LastEvent
  RecoveryTeleport 0.47s ago
```

Entity/debug references should use validated handles/identities rather than assuming long-lived raw entity references remain valid.

## 10. ValveResourceFormat — use offline, not in server runtime

ValveResourceFormat can parse Source 2 resources and entity lumps and can support Entity I/O graph analysis.

A future offline developer tool may use this to reduce manual map research:

```text
map resources
→ ValveResourceFormat
→ entity lumps / I/O graph
→ ZEPVE.MapAnalyzer
→ MapScanReport
→ optional suggested override skeleton
→ human review
```

Possible report data:

```text
teleport count
trigger_push count
moving platform candidates
counters
breakables
likely Boss counters
likely stage relays
possible nuke signals
NAV availability
```

Do not make ValveResourceFormat a server-runtime dependency unless a future requirement proves that necessary.

## 11. Refined target structure

The research suggests the following additions without changing the core repository model:

```text
CS2-ZE-PVE
├─ ZEPVE.Abstractions
│  ├─ IBotTargetProvider
│  ├─ IBotAwarenessApi
│  ├─ IMapStateApi
│  └─ IBossStateApi
│
├─ ZEPVE.Core
│  ├─ PlayerRegistry
│  ├─ ZepvePlayerContext
│  ├─ ZombieContext
│  └─ lifecycle coordination
│
├─ ZEPVE.BotAI
│  ├─ Targeting
│  ├─ Awareness
│  ├─ Profiles
│  └─ Diagnostics
│
├─ ZEPVE.Map
│  ├─ MapDefinition
│  ├─ MapPlanCompiler
│  ├─ MapEntitySelector
│  ├─ MapSignal
│  └─ MapRuntime
│
└─ tools/
   └─ ZEPVE.MapAnalyzer        # later/offline
```

Independent repositories remain outside this main-source tree:

```text
ZEPVE-Navigation  -> Runtime Trails, Recorded Routes, movement, progress and Recovery
ZEPVE-HUD         -> presentation only, after stable public state APIs exist
ZEPVE-WeaponSystem -> weapon configuration/purchase/ammo/damage policy
```

Do not duplicate these independent component implementations under `CS2-ZE-PVE/src/` merely for directory symmetry.

## 12. Updated implementation priority

### Immediate

1. Reproduce and tie the working legacy baseline to build/dependency/runtime evidence.
2. Define migration authority/current writers before transferring gameplay behavior.
3. Add Core identity/registry/lifecycle invalidation as an observer while legacy remains the gameplay writer.
4. Transfer Core lifecycle authority one responsibility at a time with an explicit old-writer disable path.
5. Add structured lifecycle diagnostics / bounded Flight Recorder events early.

### After the lifecycle foundation

6. Introduce BotAI authoritative `AssignedTarget` as a new capability.
7. Reproduce the current post-teleport awareness problem with evidence rather than logs alone.
8. Validate minimal Valve Bot profile/awareness changes in ZEPVE-Lab.
9. Build the hybrid Navigation baseline: native progress → per-human Trail → layered recovery.
10. Implement no-NAV movement takeover only after the movement-control PoC succeeds.
11. Introduce the minimum useful `MapDefinition → MapPlan → MapRuntime` pieces during Map/CS2Fixes integration.
12. Add real ZE configuration corpus tests before broad map-support claims.

### Later

13. Recorded Route authoring and visualization.
14. HUD/WeaponSystem migration on top of stable public state APIs and verified behavior contracts.
15. Director through Core spawn pressure and BotAI profile policy.
16. Offline `ZEPVE.MapAnalyzer` and compatibility-report tooling.

## 13. Explicit non-goals from this research

Do not introduce these only because another project has them:

- a database layer for core gameplay;
- a generic scripting engine;
- an in-server GUI;
- permanent per-tick forcing of broad Valve Bot state;
- full movement recording for ordinary Runtime Trails;
- a separate repository for every DLL;
- a new diagnostics DLL before the diagnostic API has independent value;
- automatic generated map overrides without human review;
- a second respawn scheduler while ZombieReborn/compatibility remains the active executor;
- a complete BotPool/lease system during the first Core migration slice.

## 14. Engineering rules reinforced by the research

```text
One authoritative owner per state.
One active writer during migration.
Lifecycle invalidation is explicit and wider than slot/spawn identity alone.
Hot paths do only necessary allocation-light work.
Configuration is parsed/validated before runtime use.
Map entity discovery belongs to Map, not HUD.
Engine-unstable behavior sits behind adapters and is proven in Lab first.
Logs describe transitions; bounded diagnostics explain failures.
Real map/config corpora validate compatibility claims.
Prefer native Valve behavior when it works; patch only the missing behavior.
```

These rules should guide implementation choices even when individual type names or module layouts change.
