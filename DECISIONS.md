# Architecture Decisions

Only record decisions future contributors or Codex sessions might otherwise reopen.

- **ADR-001 — ZE first.** ZEPVE is a ZE-first PvE runtime. Standard-map Survival/Horde support is secondary.
- **ADR-002 — Suite integration repository.** `CS2-ZE-PVE` is the user-facing integration/release repository; independently useful production components may live in separate repositories and are pinned here.
- **ADR-003 — Core does not own Trail data.** Trail recording, movement and recovery belong to Navigation.
- **ADR-004 — Navigation order.** Prefer `Native navigation -> Trail navigation -> Recovery`.
- **ADR-005 — Runtime Trails are the default no-NAV route source.** Humans generate routes automatically while playing; normal map support must not require hand-authored checkpoint chains.
- **ADR-006 — Teleport is recovery.** Do not use continuous teleport as normal locomotion.
- **ADR-007 — CS2Fixes remains a compatibility layer.** Keep mature ZE map semantics where useful; ZEPVE owns PvE rules and Bot lifecycle.
- **ADR-008 — One authority per state.** Do not let ZEPVE and another system independently own the same respawn/movement/round state.
- **ADR-009 — Optional native movement.** Try existing movement-control APIs before creating a custom MovementBridge.
- **ADR-010 — User docs are bilingual.** English and Simplified Chinese are first-class user-facing documentation.
- **ADR-011 — Developer docs stay compact.** Avoid duplicated translations for Codex/internal docs unless translation materially helps contributors.
- **ADR-012 — No premature scripting/database systems.** Add complex subsystems only after a concrete ZE/PvE need exists.
- **ADR-013 — Production components are pinned.** The suite references independent production components by exact Git commit/submodule revision; it does not silently track moving component branches.
- **ADR-014 — Lab never ships.** `ZEPVE-Lab` is an evidence/PoC repository and is never a production submodule or release dependency.
- **ADR-015 — Component development and suite integration are separate reviews.** A Navigation change is reviewed in `ZEPVE-Navigation`; the suite then receives a separate component-bump PR after validation.
- **ADR-016 — One suite release for users.** Even when development spans several repositories, server operators should normally install one ZEPVE release package assembled by `CS2-ZE-PVE`.
- **ADR-017 — Upstream first.** Missing third-party capabilities should be addressed upstream when practical; local forks exist only for clear ZEPVE-specific needs or blocked upstream work.
- **ADR-018 — Direct-main is limited to lightweight repository/docs work.** Runtime, build, dependency, component-pin and release-content changes use branch + PR; documentation/pages/templates may be committed directly to `main` when the owner allows it.
- **ADR-019 — Recorded Routes supplement runtime Trails.** Navigation may provide an in-game visual route recorder and persistent Recorded Routes for difficult sections, repeatable tests and map-author workflows. Recorded Routes reuse the TrailDriver/progress/recovery stack and do not create a second checkpoint-navigation system.
- **ADR-020 — Rich motion replay is exceptional.** Full or near-full input replay is not the normal route format. A short `MotionClip` mechanism may be added only for isolated movement sequences that cannot be handled reliably by route nodes and movement markers.
- **ADR-021 — ZEPVE AssignedTarget is authoritative for zombie pursuit.** Each zombie has an explicit assigned human target. Valve's current Enemy/visibility state is transient combat perception and must not be used as the authority for whether the Bot should continue pursuing a human.
- **ADR-022 — Recovery teleport includes target synchronization.** A recovery teleport is not complete after changing position. Navigation/route binding must be synchronized with `AssignedTarget`, followed by a short enemy-reacquisition window. Prefer normal engine reacquisition first; explicit Bot AI-state writes are a validated fallback only and must not blindly force visibility.
- **ADR-023 — BotAI owns target and awareness state.** `ZEPVE.BotAI.dll` owns `AssignedTarget`, target selection/distribution, awareness assistance and enemy-reacquisition policy. `ZEPVE-Navigation` consumes the assigned target and owns only route selection, locomotion and movement recovery.
- **ADR-024 — Preserve native perception before inventing a threat system.** ZEPVE should keep Valve hearing/sound investigation where useful and use small event-triggered awareness assists such as wake/active, ignore-enemies reset, alert windows and look-around reset only when validated. Do not introduce a custom footstep/gunshot hate table unless runtime evidence shows native perception is insufficient.
- **ADR-025 — BotAI starts as an in-suite DLL, not a separate repository.** Create `ZEPVE.BotAI` as a separate project inside `CS2-ZE-PVE`. Split it into an independent repository only if it later develops a stable reusable contract and independent release/test value.
- **ADR-026 — Legacy source is a regression baseline, not the target architecture.** Existing `Kzen-ZRPVE`, `Kzen-WeaponBalance` and `Kzen-ZEAssist` sources are preserved under `legacy/` while behavior is classified and migrated. New features should not create a second production implementation inside `legacy/`.
- **ADR-027 — HUD and WeaponSystem are independent migration targets.** `ZEPVE-HUD` owns presentation and `ZEPVE-WeaponSystem` owns PvE weapon policy. Creating these repositories does not automatically make them suite dependencies; each must establish a reproducible build, stable boundary and tested integration contract before being pinned and shipped.
- **ADR-028 — Migration keeps exactly one active writer.** During legacy extraction, the current implementation remains authoritative until its replacement has been implemented, verified and the old execution path is explicitly disabled. A new owner existing in code is not enough to complete a handoff. Migration details live in `MIGRATION_AUTHORITY.md`.
- **ADR-029 — Delayed actions require lifecycle identity validation.** Slot identity alone is insufficient for delayed work. Actions must be invalidated by the relevant plugin/map/round/connection/pawn lifetime, with an additional target/binding version when needed.
- **ADR-030 — Respawn ownership separates policy from execution.** Core may own respawn policy while a validated ZombieReborn/compatibility adapter remains the sole executor. Do not create a second respawn scheduler merely to make Core the direct caller.
- **ADR-031 — Component pinning and runtime readiness are distinct.** A gitlink/pinned design revision may exist before a component is runtime verified. Release documentation must distinguish a registered/integration reference from a production-validated component revision.
- **ADR-032 — Lifecycle authority uses one shared Core provider.** `SuiteRuntime.Current` exposes Core's read-only contract from one CounterStrikeSharp shared assembly; it is a provider reference, not another registry. Consumers own disposable work scopes and never manufacture lifetime generations.
- **ADR-033 — Round migration ships as a gated pair.** The adapted legacy DLL contains no quota/team/infection policy executor. New Core enables gameplay only when that bridge exists; missing dependencies fail closed, without reviving a legacy writer. Upgrade/rollback Core, ZRPVE and the shared ABI together while the server is stopped.
- **ADR-034 — Hot reload preserves owned deadlines; late load does not guess them.** An atomic hot reload carries only an immutable policy plan through the shared ABI and rebinds work to a fresh plugin lifetime. Manual unload/late load observes existing players but waits for a new round to establish policy, preserving native gameplay instead of inventing an infection/release deadline.
- **ADR-035 — BotAI targets bind both Core identities and a module/version.** Stable least-assigned distribution balances live humans with minimal churn. Target-specific work validates bot and human lifecycle, Released/live roles, BotAI GUID and BindingVersion. Reload never restores old target work. No second player registry.
- **ADR-036 — v0.2d reacquisition is bounded observation only.** Exact BotController source/API review establishes disjoint control boundaries; BotAI makes no native perception/movement writes. Three-second observations with ten-second cooldown report engine success/timeout, not causal repair. Native assist candidates require Lab evidence; lack of evidence must not produce speculative field writes.
- **ADR-037 — v0.3 is the Navigation baseline; advanced traversal is v0.4.** v0.3 ends at reliable AssignedTarget-driven Native -> Trail -> Recovery ownership, lifecycle correctness, basic no-NAV pursuit, diagnostics, matched installation and rollback. v0.3 already uses the leased UserCmd movement backend; timed/signed-subtick payloads, scoped traversal view, automatic MotionClip capture and complex traversal fidelity are v0.4 capabilities even when experimental code already exists on mixed-history PRs.
- **ADR-038 — Route selection and traversal execution are separate responsibilities.** Runtime Trail or a future persistent RouteGraph decides where the Bot should go. A short `MotionClip` or other typed traversal action only executes an already-selected local maneuver. Replay must not become the route planner or a general gameplay-recording system.
- **ADR-039 — Traversal view ownership is scoped and exceptional.** Ordinary Native/Trail pursuit does not own view. Only an active validated traversal action may temporarily acquire scoped facing/view control through the same exclusive router/lease; cancellation, invalidation or completion returns view control immediately. Persistent map routes belong to v0.5 authoring.
- **ADR-040 — v0.3 movement backend is the focused leased BotController path.** The clean baseline uses the existing `PlayerRunCommand` dispatcher with one router, one exclusive owner/lease, one current intent, application-time identity/lifecycle/revision/TTL/native-handle validation and managed cancel/drain. No parallel movement hook, anonymous replay, perception/view/pawn-state writer or Lab runtime dependency is allowed. The native router/shared adapter is process-resident; native replacement requires a stopped server.
- **ADR-041 — Navigation handoff ships only as a matched gated package.** The adapted legacy runtime must physically retire its Trail/watchdog/recovery scheduler/teleport writer before Navigation is authoritative. Core/BotAI authority does not move. Suite gitlink, component checkout, source revision, ABI/build profile, produced artifacts, manifest, install inventory and rollback inventory are one matched evidence set; hash consistency alone is not artifact provenance.
- **ADR-042 — Recovery permission is separate from geometry and fails closed when unknown.** A hull-safe/grounded destination is not automatically allowed by ZE stage or map semantics. Until a canonical map permission source exists, unknown permission must reject Recovery teleport. Recovery remains final fallback and may not be used to hide baseline pursuit or traversal failures.
- **ADR-043 — ZE and ZR share one persistent `MapTraversalGraph`.** Do not create separate traversal engines for ZE and ZR. The graph contains Regions, Routes, Nodes and typed TraversalEdges. ZE primarily consumes curated route/stage progress; ZR primarily consumes dynamic target-region reachability. Both reuse the same traversal execution, progress and failure semantics.
- **ADR-044 — Human recording is authoring evidence, not the runtime route format.** A recorder may capture rich Human movement temporarily, then simplify it into graph Nodes/Regions/Edges and traversal candidates. Ordinary route geometry must not be stored or executed as a full per-tick UserCmd movie. Prefer primitive traversal; use short bounded MotionClip only when a selected local edge requires it.
- **ADR-045 — ZE backtracking is bounded by route legality.** A Bot may turn around for nearby combat inside a legal local region/stage, but it must not blindly reverse a route, cross a forbidden stage/segment boundary or reverse a `ForwardOnly` edge. If AssignedTarget is no longer legally reachable through the current graph, Navigation reports route-unavailable and BotAI decides whether to rebind.
- **ADR-046 — ZR uses reachability regions plus typed movement-skill links.** ZR does not require a fixed spawn-to-end recording. Persistent map knowledge describes camp/ground/platform Regions and difficult links such as jump/crouch-jump/drop/ladder/short MotionClip traversal. Native NAV should handle ordinary sections where useful; Runtime Trail remains fallback for unknown/unrecorded sections.
- **ADR-047 — Route authoring is chat-first and world-visible.** The first useful v0.5 authoring workflow should favor short admin chat commands, automatic raw-capture simplification/classification, in-world nodes/edges/Entry/Exit visualization and single-edge/route tests. A rich CustomHud/offline editor is optional later and must not block core authoring.
- **ADR-048 — External Bot enhancers must yield to Navigation ownership.** Optional Bot-Improver-style movement, aim or FOV helpers may coexist only through explicit ownership/arbitration. While Navigation owns movement or scoped traversal view, external modules must not mutate the same domain. Exit/Abort releases ownership immediately.
- **ADR-049 — `MapTraversalGraph` may expose read-only knowledge, not shared movement mutation.** After the graph is stable, other modules may consume versioned immutable Region/Route/Edge/reachability/context snapshots. Mutating local traversal must be requested through Navigation; consumers must not bypass MovementBridge or modify Navigation internals.
- **ADR-050 — Bot-Improver mechanisms are evidence inputs, not a production dependency bundle.** Adopt narrow patterns such as generation-safe work, perception diagnostics, event-triggered windows, spatial zone indexing and validated native patch transactions. Broad AI patches, direct pawn velocity writes, permanent visibility forcing or a second movement hook require separate evidence and are not implicitly authorized by compatibility research.
- **ADR-051 — Human players never become Zombies in ZEPVE PvE.** Human death changes lifecycle state, not gameplay role. A Human may respawn, wait, spectate or participate in a team wipe, but ZEPVE does not convert a Human player into a Zombie player; Zombie gameplay actors are Bots. Respawn policy remains Core-owned and execution stays behind the existing validated respawn compatibility boundary.
- **ADR-052 — Normal Human respawn rejoins through a live Human anchor.** When PvE policy permits respawn and at least one valid Human remains alive, prefer relocating the newly spawned Human directly to a validated live Human pawn rather than searching arbitrary nearby safe geometry. Do not reuse Zombie Navigation Recovery destination search for Human respawn. If no valid live Human anchor exists, do not invent a geometric teleport destination; treat it as wipe/wait unless a future MapPlan explicitly authorizes a checkpoint.
- **ADR-053 — Knockback is route deviation, not a special Recovery mode.** For ordinary ZE Walk/route movement, weapon knockback does not reset, replay, snap or teleport a Bot back onto the recorded path. Runtime treats the Bot's resulting physical position as a disturbance: continue locally when legal, bounded-rejoin the current route/region, then graph-replan if necessary. Recorded routes describe map progression/corridors rather than mandatory per-tick positions. Recovery remains the separately permitted final fallback.
